# provider-integrator — правила проекта для Claude Code

Инструмент принимает OpenAPI-спецификацию платёжного провайдера и детерминированно генерирует
Ruby-сервис под контракт `Provider::BaseService`, `INTEGRATION.md`, `fixtures.json` и вспомогательные файлы.
Хакатон Hack.Genesis 2026, заказчик Space Payments. Полный план — `docs/PLAN.md`, ТЗ с эталоном и разбалловкой — `docs/TZ.md`,
входная спека — `docs/provider_api.yaml`. Перед любой работой прочитай эти три файла целиком.

## Жёсткие ограничения (нарушение = дисквалификация команды)
- Весь код репозитория — Ruby (≥ 3.3). Никаких Node/Python/Go, кроме `Dockerfile`/`compose.yaml`/`Rakefile`/YAML/ERB.
- **Никаких нейросетей, LLM, ML, внешних API анализа в рантайме продукта.** Только правила, словари, регулярные выражения, взвешенный скоринг. Не добавляй гемы, которые ходят в сеть при генерации.
- Только open-source зависимости (MIT/BSD/Apache/Ruby). Перед добавлением гема проверь лицензию и укажи её в комментарии Gemfile.

## Архитектурные инварианты
- Конвейер: `Parser.call → ProviderSpec (JSON-сериализуемый IR) → Generator.call → файлы → OutputValidator`. Генератор не читает OpenAPI; парсер не знает о Ruby-шаблонах (отдаёт семантику: `{conversion: {type: multiply, value: 100}}`, а не строку кода).
- Детерминизм: одинаковый вход → байт-в-байт одинаковый выход. Запрещены `Time.now`, `rand`, `SecureRandom`, `Hash#inspect`, `object_id` в чём-либо, влияющем на вывод. Ключи сортируются; порядок операций — по порядку в спеке.
- Что из спеки не выводится — не угадывается: `TODO(confidence …)` в коде + событие `W…` в отчёте. Критичные выводы (единицы суммы, условная обязательность, подпись, статус-маппинг) **всегда** попадают в `generation_report.json` и в INTEGRATION.md → «Требует подтверждения», даже при высокой уверенности.
- Спека — недоверенный ввод: `Psych.safe_load`, ограничение размера/глубины, имена из спеки экранируются через `Inflector` (зарезервированные слова Ruby, спецсимволы), никакого `eval`/`send` с пользовательскими строками, стек-трейс пользователю не показывается (только `--verbose`).
- Ничего провайдер-специфичного в `lib/`: `grep -ri novapay lib/` должен быть пуст (есть тест). Всё знание о провайдерах — в `dictionaries/*.yml` и в спеке.
- Канон Space Payments — только в `dictionaries/canonical_contract.yml`. Не хардкодь статусы/коды/хелперы в шаблонах.
- Внешне генерируемый сервис повторяет эталон из `docs/TZ.md` (имена методов, `STATUS_MAP`, `ERROR_MAP`, структура `private`-хелперов, формат вывода CLI). Внутри — лучше эталона по списку в `docs/PLAN.md §1 п.5`.

## Стиль кода
- `frozen_string_literal: true` везде; RuboCop с конфигом репозитория, `rubocop -A` перед коммитом; никаких `rubocop:disable` без обоснования в комментарии.
- Небольшие классы с одной обязанностью, `Struct`/`Data` для моделей, явные `Result`-объекты вместо исключений на границах модулей. Исключения — только для действительно фатального (`SpecError`, `GenerationError`) и ловятся в `Pipeline`.
- Zeitwerk-совместимая структура: имя файла = имя константы.
- Публичные методы — с короткой док-строкой «что и зачем». Комментарии объясняют решения, не пересказывают код.
- Логика не живёт в ERB: шаблон получает готовую `TemplateData`. В ERB — только `<%= %>`, `<% each %>`, `<% if %>`.

## Тесты
- RSpec. Каждый анализатор — unit-тесты на позитив, негатив и неоднозначность. Golden-тесты на все спеки в `spec/fixtures/specs/`; обновление только через `rake golden:update` с осмысленным диффом в коммите.
- Тест детерминизма (два прогона → одинаковые SHA-256), тест анти-хардкода, тест «сгенерированный сервис проходит `Prism`», тест «сгенерированный RSpec зелёный против `base_contract.rb`».
- Не запускай сгенерированный код без WebMock. Реальных сетевых вызовов в тестах нет.

## Как работать
- Работай волнами из `docs/PLAN.md §10`. Волна не считается законченной, пока не выполнен её критерий и не зелёный `bundle exec rspec && bundle exec rubocop`.
- Перед изменением контракта `ProviderSpec` (`docs/PLAN.md §3`) — остановись и спроси: контракт общий для трёх разработчиков.
- Коммит на каждую завершённую задачу, сообщение в стиле `wave1(parser): operation classifier with weighted scoring`.
- Если ТЗ и план расходятся — приоритет у `docs/TZ.md` (эталон и разбалловка), затем у ответов экспертов в `docs/PLAN.md §4`, затем у плана.
- Не добавляй фичи вне текущей волны. Идеи — в `docs/BACKLOG.md`.
- Для длинных документов и шаблонов используй `/ruby-cli-conventions` (проектный skill).
- Skill `ruby-cli-conventions` — живой документ, ты его поддерживаешь сам: в конце каждой волны сверяй его с фактическим кодом и обновляй (skill описывает код, а не код подгоняется под skill). Неприкосновенны только раздел «Жёсткие ограничения» и «Архитектурные инварианты» этого файла — если код им противоречит, правится код.
- Если в контексте окажется Rails-ориентированный skill (concerns, контроллеры, ActiveRecord, jobs) — игнорируй его рекомендации: проект не на Rails.

## Локальное окружение разработки (факты, проверено 2026-09-05)
- Машина разработки — Windows 11; Ruby 4.0.6 (`E:/Ruby40-x64`, x64-mingw-ucrt), Bundler 4.0.16. Целевая версия проекта — Ruby ≥ 3.3 (`TargetRubyVersion: 3.3`, Dockerfile `ruby:3.3-slim`): не использовать фичи 3.4+ (блочный параметр `it` и т.п.), код должен работать и на 3.3, и на 4.0.
- Shell для команд — Git Bash (`bundle exec rspec`, `bundle exec rubocop`, `bundle exec rake check`). Все файлы — LF (`.gitattributes`: `* text=auto eol=lf`, `core.autocrlf=false`); CRLF ломает golden-тесты и SHA.
- `openapi3_parser` 0.10.1 на Windows падает при доступе к операциям (`Source::Pointer::MergePointers#merge_pointers` использует `File.expand_path`, который подставляет букву диска в JSON-pointer: `["C:", "paths", ...]`). Поэтому: (1) в проекте есть шим `ProviderIntegrator::Compat` с чистой сегментной реализацией `merge_pointers`; (2) чтение спеки идёт через собственный резолвер локальных `$ref` по хэшу (`Parser::RefResolver` → `Parser::SpecReader`), а `openapi3_parser` используется для структурной валидации (`valid?`, `errors`) и как кросс-проверка.
- `bundle exec rubocop -A` на Windows перезаписывает исправленные файлы с CRLF (Ruby открывает файл в текстовом режиме). После `-A` нормализовать: `ruby -e 'Dir["lib/**/*.rb","spec/**/*.rb","Rakefile"].each{|p| s=File.binread(p); File.binwrite(p, s.gsub("\r\n","\n")) if s.include?("\r")}'` (или `rake lf`). В самом продукте RuboCop для сгенерированного кода вызывать только через API со `stdin:` и брать исправленный текст из памяти, не через запись файла.
- `ruby -e '...'` с не-ASCII текстом падает с `Encoding::CompatibilityError` (кодировка консоли IBM866): одноразовые скрипты с кириллицей класть в файл (`.rb`, UTF-8) и запускать `ruby файл`.
- Docker Desktop установлен, демон может быть не запущен — проверять `docker info` перед docker-задачами; отсутствие Docker не блокирует остальные волны.
- Гемы (все MIT, кроме указанных): openapi3_parser 0.10.1, json_schemer 2.5.0, zeitwerk 2.8.3, thor 1.5.0, pastel 0.8.0, tty-table 0.12.0, rake 13.4.2, sinatra 4.2.1, rackup 2.3.1, puma 8.0.2 (BSD-3-Clause), rubyzip 3.6.0 (BSD-2-Clause), diff-lcs 1.6.2 (MIT/Artistic/GPL — используем по MIT), rspec 3.13, webmock 3.26.4, rack-test 2.2.0, rubocop 1.90.0, rubocop-rspec 3.10.2, rubocop-rake 0.7.1. Все установлены локально и работают на Ruby 4.0.6.
